# Watchmate client ↔ server contract (v2)

This file is the **single source of truth** for the API between `client/` and `server/`. Both sides implement exactly what is written here. They don't add, rename, or omit fields. If something is missing or unclear, stop and ask the user. Don't invent a solution. Any change to this file must be approved by the user, and both sides must then apply it.

## 1. Principles

- **Identity is not the socket.** A user is a *member* with a stable `userId` and a secret `memberToken`, both issued by REST. The socket is only a delivery channel. After a reconnect the member is the same: same host role, same ready state, same messages.
- **REST handles commands and history.** Every state-changing action is a REST call that returns a result or an error.
- **The socket handles live push.** The server pushes updates. Clients emit only frequent, disposable events: playback sync, reactions, playback requests.
- **Nothing gets lost on reconnect.** On every socket `connect`, the client re-fetches the room snapshot and the messages it missed (`afterSeq`).
- **Room address and join code are different things.** `roomId` is a UUID used in the URL. It never changes. `joinCode` is a separate random code for joining by hand. The host can regenerate it.

## 2. Identifiers

| Name | Format | Generated by | Notes |
|---|---|---|---|
| `roomId` | UUID v4, lowercase (`crypto.randomUUID()`) | server | The URL is `/room-:roomId`. Validate the UUID format and answer 404 when it doesn't match. It's not uppercased. |
| `joinCode` | 6 chars from `ABCDEFGHJKMNPQRSTUVWXYZ23456789` | server | Unique among active rooms and not derived from `roomId`. Shown as `XXX-XXX`. Input is normalized: uppercase, then remove `-` and spaces. |
| `hostToken` | 48 hex chars | server | Returned only by `POST /rooms`. Used only to claim the host role on the first join. |
| `userId` | UUID v4 | server | A stable member id. It **replaces `socket.id`** everywhere that `userId` appears. |
| `memberToken` | 48 hex chars | server | The member's secret. REST: `Authorization: Bearer <memberToken>`. Socket: `auth.memberToken`. |
| `clientId` | UUID v4 | client | Idempotency key of a chat message. |
| `seq` | integer, starts at 1, +1 per message in a room | server | Chat order and sync cursor. |

## 3. Timings and limits (constants on both sides where marked)

| Constant | Value | Where | Meaning |
|---|---|---|---|
| `MEMBER_GRACE_MS` | 180000 (3 min) | server | A member with no live socket for this long is removed. |
| `ROOM_EMPTY_TTL_MS` | 180000 (3 min) | server | A room with no online members for this long is deleted, with all its data. |
| `HOST_GRACE_MS` | 30000 (30 s) | server | A host with no live socket for this long loses the role. It goes to the online member who joined first. |
| `MAX_MESSAGES` | 200 | server | Messages kept per room (oldest dropped). |
| `MESSAGE_MAX_LENGTH` | 500 | both | |
| `USERNAME_MAX_LENGTH` | 30 | both | |
| `COUNTDOWN_START` / `COUNTDOWN_INTERVAL_MS` | 3 / 1000 | both | Unchanged. |
| Socket flood limit | 15 events/s per socket | server | Extra events are **dropped**. The socket is never disconnected for flooding. |
| Client throttle | `playback-sync` ≤ 4/s, `reaction` ≤ 5/s | client | |

Rate limiters (server, per IP; behind a proxy, use the client IP from `X-Forwarded-For` when env `TRUST_PROXY=1`):

- `createRoomLimiter`: 10 per hour on `POST /rooms`.
- `joinLimiter`: 10 per 15 min on `POST /rooms/:roomId/members`, with `skipSuccessfulRequests: true`.
- `codeLookupLimiter`: 20 per 15 min on `GET /rooms/by-code/:code`, with `skipSuccessfulRequests: true`.
- `globalLimiter`: raise it to 600 per 15 min, because chat and commands now go over REST.

## 4. Data types

```ts
type RoomUser = {
  userId: string
  userName: string
  online: boolean      // has a live socket
}

type ChatMessage = {
  id: string           // server UUID
  clientId: string     // from the sender; used for dedupe
  seq: number
  userId: string
  userName: string
  message: string
  timestamp: string    // ISO 8601
}

type QueueItem  = { id: string; url: string; title: string }                 // unchanged
type Suggestion = { id: string; url: string; title: string;
                    suggestedBy: string; suggestedById: string }            // suggestedById = userId
type PlaybackState = { isPlaying: boolean; currentTime: number }            // server extrapolates currentTime when playing
type ReadyState = { readyUsers: string[]; allReady: boolean }

type RoomSnapshot = {
  room: { id: string; joinCode: string; isPrivate: boolean; createdAt: string }
  me: { userId: string }
  users: RoomUser[]    // host first
  hostId: string | null
  ready: ReadyState
  video: string        // '' = no video
  playback: PlaybackState | null
  queue: QueueItem[]
  suggestions: Suggestion[]
  lastSeq: number      // 0 if there are no messages
}
```

## 5. REST API

Base: `${VITE_API_URL}/api/v1`. Every response uses the envelope `{ success: true, data }` or `{ success: false, error: { message, code } }`. Error `message` text is in Russian.

Auth levels:
- **public**: no auth.
- **member**: `Authorization: Bearer <memberToken>`, and the token belongs to `:roomId`.
- **host**: member **and** that member is the current host.

Standard error codes:

| Code | HTTP | Meaning |
|---|---|---|
| `VALIDATION_ERROR` | 400 | Invalid request body or parameters |
| `UNAUTHORIZED` | 401 | Token missing, unknown, or expired. The client must join again. |
| `WRONG_PASSWORD` | 401 | Wrong room password |
| `FORBIDDEN` | 403 | Host-only action |
| `NOT_FOUND` | 404 | Also: unknown member id in `POST /host` |
| `RATE_LIMIT` | 429 | |

More rules:
- Other failures that are logically invalid return `VALIDATION_ERROR`. That covers malformed JSON, `queue/next` on an empty queue, and transferring the host role to an offline member.
- Status codes: a successful create returns 201 (`POST /rooms`, `/members`, and a new message). Everything else returns 200, including a repeated `clientId`.

### Rooms and access
| Method & path | Auth | Body | `data` |
|---|---|---|---|
| `POST /rooms` | public | `{ isPrivate?: boolean, password?: string }`. `password` is required when `isPrivate`. | `{ id, joinCode, hostToken, isPrivate }` |
| `GET /rooms/:roomId` | public | — | `{ id, isPrivate }` (no `joinCode`) |
| `GET /rooms/by-code/:code` | public | — | `{ id, isPrivate }`. Wrong code → 404. |
| `POST /rooms/:roomId/code` | host | — | `{ joinCode }`. Also broadcasts `room-update`. The old code stops working immediately. |
| `POST /rooms/:roomId/members` | public | `{ userName, password?, hostToken? }` | `{ userId, memberToken, isHost }` |
| `DELETE /rooms/:roomId/members/me` | member | — | `{ left: true }`. The member is removed immediately, and a host leaving hands the role over immediately. |
| `GET /rooms/:roomId/state` | member | — | `RoomSnapshot` |

The rules for `POST /members`:
- A **private room always requires the correct `password`**, whether the user arrived by link or by code. The only exception is a valid `hostToken`, which skips the password check.
- A matching `hostToken` makes the member host, but only if the room has no host or the current host is offline.
- **Vacant host role:** when the role becomes free and nobody is online to take it, `hostId` is `null`. No `host-update` is sent in that case. The first member to come online takes the role, and then `host-update` is sent.
- When a member leaves or is removed, the server broadcasts `users-update`. It also broadcasts `host-update` if the role moved, and `ready-update` if the ready state changed.
- Each call creates a new member. The client never calls it again while it holds a valid `memberToken`.

### Chat
| Method & path | Auth | Body / query | `data` |
|---|---|---|---|
| `GET /rooms/:roomId/messages?afterSeq=N` | member | `afterSeq` defaults to 0 | `{ messages: ChatMessage[], lastSeq }`. Messages with `seq > N`, oldest first. |
| `POST /rooms/:roomId/messages` | member | `{ clientId, message }` | `ChatMessage` |

`POST /messages` is **idempotent by `clientId`**. When the same `clientId` repeats, the server returns the existing message and doesn't broadcast it again. After it stores a new message, it broadcasts `message-new` to the room, including the sender.

### Video, queue, and suggestions
| Method & path | Auth | Body | `data` | Broadcast |
|---|---|---|---|---|
| `PUT /rooms/:roomId/video` | host | `{ url }` | `{ video }` | `video-update` |
| `DELETE /rooms/:roomId/video` | host | — | `{ video: '' }` | `video-update` with `''` |
| `GET /rooms/:roomId/queue` | member | — | `QueueItem[]` | |
| `POST /rooms/:roomId/queue` | host | `{ url, title? }` | `QueueItem[]` | `queue-update` |
| `DELETE /rooms/:roomId/queue/:itemId` | host | — | `QueueItem[]` | `queue-update` |
| `PATCH /rooms/:roomId/queue/:itemId/play` | host | — | `{ video, queue }` | `video-update`, `queue-update` |
| `PATCH /rooms/:roomId/queue/next` | host | — | `{ video, queue }` | `video-update`, `queue-update` |
| `PATCH /rooms/:roomId/queue/reorder` | host | `{ fromIndex, toIndex }` | `QueueItem[]` | `queue-update` |
| `GET /rooms/:roomId/suggestions` | member | — | `Suggestion[]` | |
| `POST /rooms/:roomId/suggestions` | member | `{ url, title? }` | `Suggestion[]` | `suggestions-update` |
| `PATCH /rooms/:roomId/suggestions/:id/accept` | host | — | `{ queue, suggestions }` | `queue-update`, `suggestions-update` |
| `DELETE /rooms/:roomId/suggestions/:id` | host | — | `Suggestion[]` | `suggestions-update` |

### Ready and host
| Method & path | Auth | Body | `data` | Broadcast |
|---|---|---|---|---|
| `POST /rooms/:roomId/ready/toggle` | member, **non-host** | — | `ReadyState` | `ready-update`. The host gets `FORBIDDEN`. The countdown never starts on its own. |
| `POST /rooms/:roomId/ready/start` | host | — | `{ started: true }` | `countdown` 3→0, then `ready-update` (ready state reset). `VALIDATION_ERROR` if `allReady` is false or a countdown is already running. Changing or clearing the video (`PUT`/`DELETE /video`, queue play or next) **cancels** a running countdown: no further `countdown` events are sent, and clients drop the countdown on `video-update`. |

**The host is ready by default** and never counts. `readyUsers` lists the ready **viewers**: every ready `userId` except the current host, whether online or offline. `allReady` is true when **every online viewer** is ready. It's also true when no viewers are online, so a host alone can start. Offline members (still within `MEMBER_GRACE_MS`) don't block it, and their ready state is kept across reconnects. The server recomputes the state and broadcasts `ready-update` whenever someone's online status changes or the host role changes. The client shows viewers a Ready toggle, and shows the host a Start button only while `allReady` is true.
| `POST /rooms/:roomId/host` | host | `{ userId }` (an online member) | `{ hostId }` | `host-update` |

Removed: `POST /rooms/:roomId/verify` (now part of `POST /members`), `GET /rooms/:roomId/users` (now part of `/state`).

## 6. Socket.IO

### Connection
The client connects with a callback, so every reconnect sends the current token:
```ts
io(SOCKET_URL, { auth: (cb) => cb({ roomId, memberToken }) })
```
- The server validates the connection in `io.use`.
  - On success it sets `socket.data = { roomId, userId }`, joins the socket to `roomId`, marks the member online, cancels that member's grace, host, and room timers, and broadcasts `users-update`.
  - On failure it rejects with `new Error('UNAUTHORIZED')`. The client clears its token.
  - When the per-IP connection cap (10) is exceeded, it rejects with `new Error('RATE_LIMIT')`. The client keeps its token and retries after 5 s, because Socket.IO doesn't retry after a middleware rejection.
- One member may have several sockets (for example, several tabs). The member is **offline** only when the last one disconnects. That starts the `MEMBER_GRACE_MS` timer, plus the `HOST_GRACE_MS` timer if the member is host and the `ROOM_EMPTY_TTL_MS` timer if nobody is left online. Then the server broadcasts `users-update`.
- **No `join-room`, and no `roomId` in any payload.** The server takes both from `socket.data`.

### Client → server (fire-and-forget; the server validates every payload and silently drops invalid ones)
| Event | Payload | Who | Server action |
|---|---|---|---|
| `playback-sync` | `{ isPlaying: boolean, currentTime: number }` | host | Store the playback state, then relay `playback-update` to the others |
| `reaction` | `{ emoji: string }` (≤ 8 chars) | member | Broadcast `reaction` |
| `playback-request` | `{ type: 'pause' \| 'play' \| 'change-video', videoUrl?: string }` | non-host | Store the request as pending, then send `playback-request-notify` to the host's sockets only |
| `playback-request-answer` | `{ requestId: string, accepted: boolean }` | host | Close the pending request, then send `playback-request-answered` to the requester's sockets only. Unknown or already answered ids are ignored. Pending requests are dropped when the room is deleted. |

### Server → client
| Event | Payload |
|---|---|
| `users-update` | `RoomUser[]` |
| `host-update` | `string` (hostId) |
| `room-update` | `{ joinCode: string }` |
| `message-new` | `ChatMessage` |
| `video-update` | `string` (`''` = cleared) |
| `playback-update` | `PlaybackState` |
| `playback-request-notify` | `{ id, fromUserId, fromUserName, type, videoUrl? }` |
| `playback-request-answered` | `{ requestId, type, accepted }`. Sent to the requester. The host sends `accepted: true` after performing the action, and `false` on "Decline" or when it closes the toast. |
| `ready-update` | `ReadyState` |
| `countdown` | `number` |
| `queue-update` | `QueueItem[]` |
| `suggestions-update` | `Suggestion[]` |
| `reaction` | `{ userId, userName, emoji }` |
| `session-ended` | `{ reason: 'room-deleted' \| 'member-removed' }`. Sent before the server closes that member's sockets. |

Removed events: `join-room`, `chat-message`, `chat-history`, `share-video`, `clear-video`, `queue-add`, `queue-remove`, `queue-play`, `queue-reorder`, `queue-next`, `suggest-video`, `accept-suggestion`, `reject-suggestion`, `toggle-ready`, `transfer-host`, `local-file-update`.

`SOCKET_EVENTS` on both sides contains **exactly** the events in this section.

## 7. Client flows

**Create a room:**
1. `POST /rooms`.
2. Save `hostToken_{id}`.
3. `POST /members` with `hostToken`.
4. Save `memberToken_{id}`.
5. Navigate to `/room-{id}`.

**Join by code:** the home page has a code field.
1. `GET /rooms/by-code/:code` → `{ id, isPrivate }`.
2. Navigate to `/room-{id}`.

**Open `/room-:roomId`:**
1. `GET /rooms/:roomId`. On 404, show "Комната не найдена".
2. If there is no `memberToken_{roomId}`, show the join form: name, plus a password when `isPrivate`. Then call `POST /members`. On `WRONG_PASSWORD`, show an error.
3. Connect the socket.

**On every socket `connect`, including reconnects:**
1. `GET /state`: replace all room state.
2. `GET /messages?afterSeq=<lastSeq>`: merge into the chat, dedupe by `id`, sort by `seq`. On the first load `lastSeq` is 0.
3. `lastSeq` is a **contiguous cursor**: every message with `seq <= lastSeq` has been received. It advances to `data.lastSeq` of a `GET /messages` response. It advances through `message-new` and `POST` responses only while there's no gap (`seq === lastSeq + 1`, and so on). It never jumps to the max seen seq, because a message received out of order (for example, your own retried POST right after a reconnect) would then skip the gap before it.

**Sending a message:**
1. Generate a `clientId` and show the message at once with status `pending`.
2. `POST /messages`.
   - On success, replace the pending message with the server message (status `sent`).
   - On a network error or 5xx, retry with the same `clientId` (backoff 1 s, 2 s, 4 s). After that, mark it `failed` and show a "Повторить" button.
3. A `message-new` with a `clientId` the client already holds replaces that message instead of adding a duplicate.

**Connection status:** show a "Переподключение…" banner while the socket is disconnected.
- On `disconnect` with reason `io server disconnect`, call `socket.connect()`.
- On `connect_error` with message `UNAUTHORIZED`, or when any REST call returns `UNAUTHORIZED`, clear `memberToken_{roomId}` and show the join form again.
- On `session-ended`, clear `memberToken_{roomId}`. For `room-deleted`, show "Комната не найдена". For `member-removed`, show the join form.

**Leaving:** `DELETE /members/me`, then clear `memberToken_{roomId}` and `hostToken_{roomId}`, disconnect the socket, and navigate to `/`.

**sessionStorage keys:** `userName`, `hostToken_{roomId}`, `memberToken_{roomId}`. The `passwordVerified_{roomId}` key is removed.
